# API

The backend exposes one GraphQL endpoint and one REST endpoint on port 4000.

| Endpoint                                | Purpose                                         |
| --------------------------------------- | ----------------------------------------------- |
| `POST /graphql`                         | GraphQL API used by the desktop app and workers |
| `GET /experiments/:experimentId/report` | PDF report for an experiment                    |

## GraphQL

- The schema is generated by `type-graphql` into `backend/schema.gql` and synchronized to `desktop/schema.graphql`.
- Resolvers live in `backend/src/modules/*/graphql` (`auth`, `computations`, `experiments`, `files`, `storage`, `technologies`) and `backend/src/graphql` (`health`, server info).
- User JWT and service token rules for each operation: [Authentication](authentication.md).
- Client-side conventions: [GraphQL in the desktop app](graphql-client.md).
- Domain behavior of the run-related operations: [Experiments and computations](../domain/experiments.md#graphql-behavior).

Quick check that the backend is running:

```bash
curl -sS http://localhost:4000/graphql \
  -H 'Content-Type: application/json' \
  --data '{"query":"{ health }"}'
```

## REST report

`GET /experiments/:experimentId/report` returns a PDF (`Content-Disposition: attachment`) that is
generated with `puppeteer` (Chromium). It contains the experiment name, description and creation
date, the graph and its settings, the source file details, the pipelines with their computing
results and machine information, and the optimization result and history.

Only the owner of the experiment can download it. The request carries the user JWT in
`Authorization: Bearer <token>`, like a GraphQL request, so a plain link or a browser tab that
is not signed in gets nothing. The desktop app downloads the report with `fetch` and saves the
response as a file (`ReportDownloadButton`). On a `401` it refreshes the session the request was
sent in, as for an `UNAUTHENTICATED` GraphQL answer, and requests the report once more with the
new access token; it shows the sign-in error only when the session cannot be refreshed.

Responses:

- `401` (with `WWW-Authenticate: Bearer`) without a valid JWT. Nothing about the experiment is
  read before the caller is known.
- `400` for a missing or invalid experiment `_id`.
- `404` when the experiment does not exist or belongs to another user: both get the same answer,
  so the response does not reveal whether someone else's id exists.
- `500` when the JWT cannot be checked (for example the database is unavailable while the user
  is loaded): the token may be valid, so the answer does not ask to sign in again.
- `500` when the PDF cannot be generated, otherwise `200` with the PDF.

The desktop app shows the download button on the details page only for `completed` experiments.

## CORS

Browsers may call the API (GraphQL and the report) only from the origins in `CORS_ORIGINS`, a
comma-separated list. The default is `http://localhost:5173,null`: the Vite dev server of the
desktop renderer and `null`, the origin of the packaged desktop app, which loads its page from a
file. The dev server always uses port 5173 (`strictPort` in `desktop/vite.renderer.config.ts`):
when the port is busy, the desktop does not start instead of moving to a port the API would block.
Requests from other origins get no `Access-Control-Allow-Origin`, so a page there cannot read
the answer. Requests without an `Origin` header (workers, `curl`) are not affected. Apollo's own
CORS is turned off (`applyMiddleware({ cors: false })`), because its default allows every origin
on `/graphql`.

CORS does not replace authentication: the API uses bearer tokens, not cookies, and every protected
operation checks the token itself.

A complete API reference (operations, examples and error messages) is planned and is not part of this
page yet.
